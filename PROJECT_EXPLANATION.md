# Digital Entertainment Voting Platform
## Comprehensive End-to-End System & Architecture Specification

---

## 1. System Overview & Strategic Purpose

The **Digital Entertainment Voting Platform** is a high-security, payment-driven competition and administrative management ecosystem designed to handle digital entertainment contests. 

### Core Architectural Principles

1. **External Video Referencing (Zero Video Hosting)**
   Contestants upload their competition entries directly to public social media platforms (**TikTok**, **Facebook**, **Instagram**, and **YouTube**). The platform stores and validates only the metadata and canonical video URLs, avoiding expensive video streaming infrastructure while maintaining authentic social engagement.

2. **Backend as the Single Source of Truth**
   The Next.js frontend functions purely as a presentation and interaction layer. It never directly interacts with database instances, payment gateways, or third-party storage APIs. Every single data access request, state transition, and payment event must be processed through the FastAPI backend API.

3. **Payment-Tied, Signature-Verified Voting**
   Votes cannot be generated by simple web requests or unverified user actions. Votes are granted **exclusively** upon the completion of a signature-verified, idempotent transaction through **Paynow Zimbabwe**.

4. **Zero-Trust Security & Fine-Grained Authorization**
   Every administrative action is governed by explicit permission checks (`events.create`, `contestants.approve`, `payments.read`, etc.), Argon2 password security, short-lived JWT tokens, and an immutable audit logging pipeline.

#### Step-by-Step Payment & Vote Processing:
1. **Initiation:** The voter selects a contestant and vote quantity (e.g., 10 votes = $10.00). The frontend calls `POST /api/v1/payments/initiate`.
2. **Pending DB State:** `PaymentService` creates a database record in state `Pending` with a unique UUID reference.
3. **Paynow Handoff:** Backend communicates with Paynow's API, passing return and result URLs, and returns the official Paynow checkout URL to the frontend.
4. **User Payment:** The user completes the transaction via EcoCash, OneMoney, or Card on Paynow's secure portal.
5. **Webhook & Verification:** Paynow posts a callback to `/api/v1/payments/paynow/callback`. 
6. **Security & Atomic Execution:**
   * The backend recalculates the SHA512/HMAC hash signature to verify authenticity.
   * `FraudDetectionService` checks for replay attacks, duplicated references, or closed competition events.
   * Inside a single **atomic database transaction**:
     * Payment record is marked as `Paid`.
     * A `VoteTransaction` audit record is created linking payment ID to participant ID.
     * The `Participant.vote_count` is incremented by the purchased vote amount.
     * An immutable `AuditLog` entry is appended.
     * Transaction is committed to PostgreSQL.

### B. End-to-End Contestant Onboarding & Lifecycle

```
Draft ──► Submitted ──► Under Review ──► Approved (Visible) ──► Disqualified / Archived
```

1. **Submission:** A contestant enters an event by submitting their personal profile and social media video link (TikTok/YouTube/Instagram/Facebook).
2. **Validation:** Backend verifies URL syntax, platform format, and event eligibility. Status is initialized as `Submitted`.
3. **Review Pipeline:** Administrators review the entry via the Admin Dashboard.
4. **Approval & Visibility:** When an admin approves the participant (`POST /api/v1/participants/{id}/approve`), their status updates to `Approved`, making them instantly queryable on public leaderboards and voting cards.

---

### C. End-to-End Administrative & Event Management Lifecycle

```
Draft ──► Upcoming ──► Registration Open ──► Voting Open ──► Voting Closed ──► Completed ──► Archived
```

1. **Event Creation:** Admins with `events.create` permission set up competition parameters (start/end dates, entry guidelines, pricing per vote).
2. **Role Verification:** Requests carry a JWT cookie/header. The backend decodes the token, extracts the user ID, checks active permissions against stored roles, and denies unauthorized requests with HTTP 403.
3. **Audit Logging:** Every modification (creating an event, changing vote multipliers, approving contestants, exporting financial reports) generates an unalterable `AuditLog` entry recording `user_id`, `action`, `resource`, `ip_address`, and timestamp.

### Security Measures Implemented
* **Password Hashing:** Argon2id via `argon2-cffi` to prevent GPU-based brute-force attacks.
* **Role-Based Access Control (RBAC):** RBAC permissions (Super Admin, Admin, Moderator) enforced via FastAPI `Depends()` authorization guards.
* **SQL Injection Prevention:** 100% parameterization via SQLAlchemy 2.0 ORM.
* **Payment Webhook Signature Verification:** Hashes incoming callback parameters with Paynow integration keys to validate request authenticity.
* **Idempotency Protection:** Duplicate callback prevention prevents double-crediting of votes even if webhooks are delivered multiple times.
* **Data Sanitization & Privacy:** Redaction policy prevents passwords, JWT tokens, API keys, and authorization headers from ever being written to logs.

### Table Definitions Overview
* `users`: Stores administrative credentials, roles, and status flags.
* `events`: Manages competition metadata, start/end dates, rules, and status flags.
* `participants`: Stores contestant profiles, video platform URLs (TikTok, YouTube, etc.), approval state, and total validated votes.
* `payments`: Stores transaction references, monetary amounts, Paynow references, and payment states.
* `vote_transactions`: Immutable audit records mapping confirmed payments to participant vote additions.
* `audit_logs`: Append-only security audit trail for compliance and security auditing.
* `activities`: System activity feed for dashboard analytics.
* `settings`: Platform configuration key-value store.

## 8. Deployment & Operational Setup

### Development Setup
1. **Backend Initialization:**
   ```bash
   cd backend
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   alembic upgrade head
   python main.py
   ```
   *Runs FastAPI backend at `http://localhost:8000` with interactive docs at `http://localhost:8000/docs`.*

2. **Frontend Initialization:**
   ```bash
   cd frontend
   npm install
   npm run dev
   ```
   *Runs Next.js web application at `http://localhost:3000`.*

### Production Infrastructure Strategy
* **Frontend:** Hosted on **Vercel** or **Netlify** with global CDN caching.
* **Backend:** Containerized via **Docker** running Gunicorn + Uvicorn workers on AWS ECS / DigitalOcean / Render.
* **Database:** Managed **Supabase PostgreSQL** instance with connection pooling enabled.
* **Monitoring:** Server health check endpoint available at `/health` providing uptime, database connection status, and operational metrics.
